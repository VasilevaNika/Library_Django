# Связывание микросервисов в Docker: документация для защиты

Три сервиса FastAPI: **recommendations-service**, **reviews-service**, **notifications-service**, плюс **монолит Django** в том же Compose.

---

## Главная общая БД — PostgreSQL монолита

- **Источник правды по схеме каталога и пользователей** — база данных, к которой подключён **Django** (`DATABASE_URL` в Compose или `DB_*` в `settings.py`). Для интегрированного стека это **PostgreSQL**, база `library`.
- **SQLite (`db.sqlite3`)** используется только если не заданы `DATABASE_URL` / `MAIN_DATABASE_URL` и не включён PostgreSQL через `DB_HOST` — то есть удобный режим «монолит без Docker», без общей БД с микросервисами.
- **Микросервисы** читают **ту же** строку подключения, что и монолит: в `docker-compose.microservices.yml` один блок **`x-database-environment`** (`DATABASE_URL`), он подмешивается (`<<: *database-environment`) во все сервисы. В коде FastAPI приоритет у `DATABASE_URL` / `MAIN_DATABASE_URL`, запасной вариант — сборка из `DB_*`. Плоские таблицы `books` и `library_users` — зеркало по `id`; актуализация — `sync_microservice_mirror`.

**Сразу после сохранения в админке** (PostgreSQL): сигналы в `library.signals` обновляют `books` и `library_users` после коммита (`transaction.on_commit`). Ошибки зеркала пишутся в лог Django (`Не удалось записать книгу … в таблицу books`).

Эндпоинт **`/recommendations/new`** сортирует по **`created_at`** (поле из монолита), затем по `id`, чтобы новая книга не терялась за сидами Alembic с большими `id` при `limit=10`.

Полное пересчитывание и `--prune` по-прежнему через:

```bash
docker compose -f docker-compose.microservices.yml exec monolith python manage.py sync_microservice_mirror
```

### Почему в микросервисах «чужие» книги и пользователи

Админка пишет в таблицы Django (`library_book`, `auth_user`, …). Сервисы рекомендаций/отзывов читают **другие** таблицы — **`books`** и **`library_users`**. Их при первом запуске заполняют **миграции Alembic** демо-данными («Война и мир», пользователь `42` и т.д.). Команда `sync_microservice_mirror` **добавляет и обновляет** записи из монолита, но **не удаляет** старые сиды, поэтому в API вы видите смесь демо и своих данных.

Чтобы оставить в `books` / `library_users` **только** то, что есть в монолите (сиды Alembic убрать):

```bash
docker compose -f docker-compose.microservices.yml exec monolith python manage.py sync_microservice_mirror --prune
```

Удаление каскадом заденет связанные `ignored_books` и `reading_list_entries`. Строки в **`reviews`** без внешнего ключа на `books` могут остаться с `book_id` удалённой книги — это редкий крайний случай.

Папки микросервисов **не обязаны** лежать внутри `Library_Django`: достаточно поправить `build.context` / `volumes` в `docker-compose` на новые пути (например `../notifications-service`). Смысл интеграции от расположения папок не меняется.

## Одна общая PostgreSQL

Все четыре приложения в Compose подключаются к **одному** контейнеру **`postgres`**, к базе **`library`**. Одна и та же переменная **`DATABASE_URL`** задаётся в якоре `x-database-environment` и наследуется монолитом и всеми микросервисами — дублировать `DB_*` в compose не требуется (локально без compose по-прежнему можно задать `DB_*` или `.env`).

Таблицы в одной БД:

- каталог и списки — миграции **recommendations** (`alembic_version_recommendations`);
- отзывы — **reviews** (`alembic_version_reviews`);
- уведомления — **notifications** (`alembic_version_notifications`).

Три отдельные таблицы версий Alembic, чтобы цепочки миграций не пересекались.

**Порядок запуска** (и миграций): `postgres` → **`monolith`** (модели Django, `django_migrations`) → `recommendations-service` → `reviews-service` → `notifications-service` (`depends_on` и `healthcheck` у монолита в Compose).

## Логика отзыва

Проверка пользователя и книги — по общей БД. После опубликованного отзыва с `book_id` книга может попасть в `reading_list_entries`; уведомление — HTTP `POST` на сервис уведомлений.

## Запуск

```bash
cd Library_Django
docker compose -f docker-compose.microservices.yml up --build
```

Порты: **8000** — монолит Django, **8001** / **8002** / **8003** — API микросервисов, **5434** — Postgres на хосте.

На главной странице монолита блок «Новинки библиотеки» запрашивает **`GET /recommendations/new`** у сервиса; в Compose задано **`RECOMMENDATIONS_SERVICE_URL=http://recommendations-service:8000`**. Локально без Docker по умолчанию **`http://127.0.0.1:8001`**. Если сервис недоступен, список берётся из ORM (как раньше).

Форма отзыва на странице книги (`/books/<id>/`) отправляет **`POST /reviews`** на **`REVIEWS_SERVICE_URL`**, при успехе монолит вызывает **`POST /notifications`** на **`NOTIFICATIONS_SERVICE_URL`** и показывает сообщение через Django messages. В Compose: **`http://reviews-service:8000`** и **`http://notifications-service:8000`**.

При переходе со старых двух контейнеров Postgres выполни сброс томов и подними заново (данные из старых томов в новую схему не переносятся автоматически):

```bash
docker compose -f docker-compose.microservices.yml down -v
docker compose -f docker-compose.microservices.yml up --build
```

Сиды пользователей/книг снова накатятся из миграций recommendations; чтобы в FastAPI остался только каталог из админки, снова выполните `sync_microservice_mirror --prune`.

## Конфликт `db.sqlite3` (git)

Файл `db.sqlite3` Django в репозитории не хранится; в `.gitignore` указан `db.sqlite3`.

## Сборка образа monolith: `pip` / DNS

Если при `docker compose build` шаг `pip install` падает с **Temporary failure in name resolution**, в `docker-compose.microservices.yml` у сервиса `monolith` в секции `build` задано **`network: host`** (как у микросервисов), чтобы сборка использовала DNS хоста.

Если собираете образ вручную: `docker build --network=host -f Dockerfile .` из каталога `Library_Django`.

Дополнительно можно задать DNS для Docker (например `8.8.8.8`) в настройках Docker или в `/etc/docker/daemon.json`.
